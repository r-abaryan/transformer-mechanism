Frozen after passing runtime preflight and complete-step profiles, before formal training, 2026-10-05. Question: can full-objective L-BFGS produce an adequately fitted reference where the original minibatch Adam procedure remains unreliable? This is development under a different procedure; optimizer, batching and stored optimizer history change together.

Seeds 3461/3463 start from their original exhaustive-feedback step-12000 checkpoints. Restore identical weights per seed. Adam restores all original moments/counters and exact history/query streams. L-BFGS starts with empty curvature history. The 615-parameter reader, normal zero-start writes, scalar beta, normalized tied Q/K, six values/classes, original labels, 32-event histories and loads 2/8/16/32 remain fixed. CPU float64, one thread, deterministic operations. Complete optimizer steps have been profiled; GPU is unused and allocated/reserved VRAM is null. CPU peak memory is unmeasured.

Full objective: L=(1/4)*sum_m mean_{h,q} CE(h,q), using every present-key query of all 768 training histories per load. Each full-gradient evaluation processes 3,072 histories, 98,304 events and 44,544 targets. Accumulate one load's gradient at a time, releasing its graph. No regularization, altered supervision or query-conditioned memory.

L-BFGS: lr=1, max_iter=1 per call, history_size=20, tolerance_grad=1e-10, tolerance_change=1e-12, strong_wolfe line search. Cap at 128 full-objective gradient evaluations per seed, including initial and trial evaluations. Before each optimizer call with at least two evaluations remaining, set max_eval=min(26,remaining-1). Inspected PyTorch 2.11 source permits max_eval+1 closure calls at the line-search limit; the extra reserve enforces the hard budget. Stop when fewer than two evaluations remain. A tolerance exit or unsatisfied bounded line search does not prove convergence. Do not extend for a failed fitting gate.

Run Adam for exactly 48 times the actual L-BFGS closure count: batch 64, original equal load cycle and exhaustive queries, lr=.003, betas=.9/.999, eps=1e-8, no decay/schedule/clipping, foreach=False. One four-load cycle processes 3,712 targets; twelve cycles process 44,544. Thus both procedures use exactly the same number of gradient targets, histories and input events per seed. Actual update counts, repeated histories, objective evaluations, optimization cost and time differ. This is exposure matching, not equal FLOPs or an isolated optimizer/noise effect. Adam is capped at 6,144 added updates per seed; L-BFGS at 128 closures. Combined maximum: 22,806,528 targets, 1,572,864 histories and 50,331,648 events across four runs.
